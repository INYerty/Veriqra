## Workflow before

1. Requirement → manually change sidebar → find/create Test Case → return and select the requirement link.
2. Case → manually open Plans → select the case again.
3. Plan → manually open Runs → select its READY plan again.
4. Run → open a snapshot → record an Attempt → return to Run to find the next case.
5. FAIL → create Defect with in-memory context; source evidence returned only to the Run.
6. Refresh restored the workspace area but not the selected object. Relationships were mostly plain IDs/text.

## Workflow after and design decisions

1. Requirement detail opens linked cases or creates a case with requirement context. Save and link remain two separate writes. If link fails, the already-created case is retained and only its link is retried.
2. Case detail continues to a new plan with that case selected, or adds it to a selected existing plan. No containing-plan membership is invented.
3. READY plan opens the existing Run creation form with the source selected. The preview uses one selected-plan detail read, not one read per plan.
4. Run shows total/recorded/NOT_RUN/PASS/FAIL/BLOCKED/SKIPPED from existing snapshots/latest Attempts. Continue selects the first NOT_RUN case in returned order.
5. Snapshot screen offers previous/next and append-or-record-and-next. Failure stays on the form; advancing happens after accepted submission.
6. FAIL opens contextual creation or association with an existing Defect. Defect evidence returns to the exact Run Case and referenced Attempt; current Test Case is a separately labelled link.

## Requirement and Test Case UX

Existing status, priority, identifiers, descriptions, preconditions and structured steps remain unchanged. Archived assets are read-only in the interface; server checks are unchanged. READY without steps is rejected locally, consistent with the server. Semantic edits may save as DRAFT and invalidate confirmed coverage links; this is explained without changing those rules.

Trace regions distinguish not loaded, loading, loaded-empty and failed. Reverse requirements load only after an explicit user action. The existing requirement-side API still entails one requirement-list read plus one trace read per requirement; it is not presented as a new bulk endpoint.

## Test Plan and Test Run UX

Plan member rows open their current Test Case. Membership add/remove retains expected-version semantics and makes the plan DRAFT. READY plans lead to contextual Run creation. Run completion availability reflects the existing requirement of at least one Attempt on every case, including FAIL/BLOCKED/SKIPPED.

## Execution, snapshots and Attempts

The snapshot consists of title, description, preconditions, priority, capture time and structured steps supplied by Run detail. Later current-case edits do not alter it. No frozen requirement coverage is claimed.

Attempts are append-only. Actor, execution time, number, actual result, duration and failure message are displayed only where the API supplies them. There are no edit/delete/overwrite controls. Previous/next uses the current Run's actual returned case order. Retrying unchanged uncertain submissions uses the same submission key scoped to project/run/case; keys are only in page memory.

Draft restoration must match the rendered form's project/run/case, not merely the requested case panel. Locale changes must not restore hidden values from a prior case. A distinct newly typed draft must not be discarded merely because an earlier submitted payload was accepted.

The initially tested single locale refresh and case-switch/locale isolation paths satisfied those guards. Final read-only review then identified rapid double-locale draft loss. The subsequent focused fix is now verified: one page-memory draft retains its project/run/case owner across overlapping locale refreshes; only the latest valid `openCase` render restores it. Changing owner, leaving the Case panel or resetting the project clears it. Already accepted matching submissions and read-only Runs do not restore input. No localStorage, backend API or second routing/state system was introduced.

## Defect UX and evidence

Failure evidence remains linked to a real FAIL. Association removal corrects the link and never removes the historical Attempt. Closing and reopening remain server-controlled. Run/history enrichment requests are shared by distinct Run and Run Case during one render. Failure is shown as unavailable, never as an empty successful retest result.

Known Defect associations created/linked in the current page session can be navigated; successful unlink removes that local association. This cache is not a complete or durable reverse lookup and is labelled accordingly.

## Traceability

CONFIRMED, NEEDS_REVIEW and REMOVED describe Requirement ↔ TestCase coverage-review relationships. They are not PASS, FAIL or deletion of a case. Removed rows remain visible and navigable. Reattach creates NEEDS_REVIEW under the existing contract. The API supplies retained relationship state, not chronological reviewer/audit history.

## Cross-navigation and deep links

`app.js` contains the small shared context helper; no routing framework is introduced. Project and relevant selected IDs are written as query values with the existing workspace hash. Selection uses replaceState; explicit cross-navigation uses pushState. Reads validate the linked project against server-accessible projects rather than falling back silently to an unrelated saved project. URLs contain IDs and UI intent only, never credentials.

Requirement/Case/Plan/Run/RunCase/Attempt/Defect context can be restored where applicable. Contextual links retain originating plan/run/attempt for return. Real anchor hrefs support a fresh tab without relying on in-memory handoff state. Sidebar native destinations clear unrelated creation intent. Back/forward popstate followed by hashchange loads the same route only once.

Generation and selected-ID checks discard stale reads/writes. Pending project selection retains its target during sidebar navigation. Existing Automation and Collaboration modules learn the view before verified project delivery; no authorization is inferred from link visibility.

## Empty, loading and error states

Existing creation entries remain available beside list empty states. Trace failure gates relationship mutation until recovery. Missing evidence selections disable submission. Selected detail and lookup failure offer scoped retry. A created case with a failed link is explicitly distinguished from failed creation. Forms retain useful draft input through lookup recovery.

## Responsive, accessibility and i18n

Existing responsive breakpoints, drawer behavior and semantic control contracts are retained. Changes reuse current flex/wrap, field, list and panel classes. Heading focus supports context changes; labels and live regions identify loading/results/errors. Outcome and relationship states have visible text, not color alone.

All new text uses matching English/zh-CN catalogs. Synchronous locale bootstrap and the no-flash mechanism remain. First-party resources use the existing generated version token; source HTML is transformed during packaging and i18n requests use the version helper. No new production JS/CSS file is introduced.

## Backend gaps and limitations

- No case-side requirements/bulk traceability read, or containing-plan read. Reverse requirements remain explicit and potentially expensive on larger projects.
- No complete HTTP Attempt → Defects read, despite internal service capability. Session-known links cannot prove all associations.
- No requirement/traceability snapshot in Run Case; current coverage must not be described as execution-time coverage.
- Create-case-and-link is not atomic; create-Defect has no idempotency key. Frontend duplicate-click guards do not guarantee retry-safe creation after an unknown network outcome.
- Plan membership and asset list APIs return whole project lists. This round does not add pagination/search endpoints.
- Unsaved drafts and uncertain-attempt keys are page memory; a full reload does not provide durable draft storage.
- An already-open older build changes only on navigation/refresh, consistent with static asset versioning.
