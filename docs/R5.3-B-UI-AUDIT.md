# R5.3-B UI Audit and Implementation Plan

Baseline: `2427fdee76853d132df1ce48a85308bec6826a14` on `r53b-design-system`, in the independent `<WORKTREE>`.

This records the source audit performed before foundation implementation. Findings below describe the baseline, not the final acceptance state. The final review separately records implementation, browser evidence and regression results.

## Baseline CSS findings

| Finding | Evidence | Planned response |
| --- | --- | --- |
| Incomplete token system | `assets/css/app.css:1` defines seven color variables only | Introduce restrained `--vq-*` colors, surfaces, typography, spacing, radius, overlay shadow, controls and transitions; retain compatibility aliases |
| Mixed action colors | `app.css:7-9` customize solid primary/focus; outline primary, link buttons and most status utilities remain Bootstrap blue | Apply one action accent through Bootstrap component variables |
| Repeated hardcoded surfaces | `app.css:13,34,55,75`; `admin.css:2,8` repeat white, borders and 12px radius | Shared surface/border/radius tokens |
| Fragmented small text scale | `.topbar-context`, `.sidebar-heading`, `.sidebar-footer`, `.project-picker`, `.asset-list-meta`, `.admin-toolbar`, `.admin-table` use many close sizes | Define a short reusable text scale with system fonts and Chinese fallbacks |
| Loose component density | `.page-heading` has 2rem spacing; `.asset-panel` padding reaches 2rem; `.asset-list-row` has 1rem vertical padding; `.empty-state` has 4rem padding | Compact shared rhythm and readable rows; retain business text |
| Marketing-like login | `.login-intro h1` reaches 5.5rem; split layout, large brand and 5rem decorative spacing | Compact authentication brand/form surface; preserve login IDs, form semantics and feedback |
| Unsystematic radius and spacing | Shared components use 8/12/14/999px radii and numerous close rem values | Small/medium radii and 4/8/12/16/24/32 spacing scale |
| Repeated responsive blocks | `app.css:101,103,104,110` repeat 767px rules | Consolidate shared wrapping and retain justified page exceptions |
| Focus override | `app.css:4` is the only custom `!important` declaration | Visible keyboard focus through shared tokens; keep necessary Bootstrap utility overrides narrowly scoped |

| Archived project looks active | `app.js:69` toggles `.is-archived`, but no baseline CSS rule consumes it; `.status-pill` is always green | Explicit archived/neutral styling and contrast regression contract |

There are no inline `style` attributes in the eleven baseline HTML pages and no page-local `<style>` blocks. Cleanup should target verified duplication, not remove values mechanically. Baseline custom CSS totals 13,926 bytes (`app.css` 12,083; `admin.css` 1,843). Custom JavaScript totals 198,170 bytes. Bootstrap and jQuery are local vendor assets; no additional framework, font CDN or large dependency is needed.

## Components and state inventory

Buttons, icon-like drawer toggles, inputs, selects, textareas, checkboxes and labels use existing Bootstrap classes. Cards/panels, definition grids and QA rows use shared application classes. Admin dynamically creates scrollable Bootstrap modals, filters, table wrappers and pagination. Alerts and local feedback are present throughout. Loading is a session spinner or live status text; empty states range from `.empty-state` panels to short muted paragraphs. No toast producer or toast HTML currently exists; shared toast styling can be ready without adding a new notification feature.

| Existing status | Baseline tone | Adoption constraint |
| --- | --- | --- |
| ACTIVE, READY, CONFIRMED, PASS, COMPLETED | Success | Preserve exact machine value and localized label |
| DRAFT, ARCHIVED, REMOVED, CANCELLED, NOT_RUN, INACTIVE | Neutral | Archived project must become neutral |
| NEEDS_REVIEW, BLOCKED, REOPENED | Warning | Same state receives one shared tone |
| IN_PROGRESS | Bootstrap primary | Use restrained shared information tone |
| SKIPPED, RESOLVED | Information | Keep business meaning; choose shared tone explicitly |
| FAIL and Defect OPEN | Danger | FAIL remains danger; OPEN should use the same non-failure state tone across modules |
| Collaboration OPEN/IN_PROGRESS/SUBMITTED/ACCEPTED, membership and handoff states | Plain text | Add shared visual semantics without changing transitions, permissions or labels |
| Admin ACTIVE/DISABLED and login results | Plain text | Apply the same palette while preserving table data |

The mapping evidence is in `test-assets.js:42`, `execution.js:32`, `defects.js:22`, `automation-imports.js:20`; Collaboration renders state text in `renderTasks`, `renderTaskDetail`, member/manager renderers and `renderOffers`. Shared status presentation should support success/warning/danger/info/neutral and avoid implying all open work is a failure.

## Responsive and accessibility risks

The baseline sidebar is fixed below 992px and controlled only through `.open` and `aria-expanded`; it has no backdrop, Escape dismissal, scroll locking or focus management. A shared drawer controller can improve these interactions while keeping existing IDs and routing.

The topbar uses a fixed 68px height with several non-wrapping controls. Admin brand markup has bare text while the main brand has an inner span; the old 480px font-size hiding rule needs consistent markup and real browser inspection. The asset detail heading action wrapper (`index.html:81`) lacks wrapping. Long task/group names, IDs and transaction references must wrap within bounded content. `.content` already has `min-width:0`; Admin tables already have a local scrolling wrapper.

Browser acceptance must inspect 1280px and 375px, with desktop layout awareness at 1440/1024/768. Check navigation, drawer, current project, section switch, task filter/pagination/selection, modal open/close, focus, language and back/forward. Complex tables may scroll inside their wrappers; the entire page must remain bounded. Test both English and zh-CN, including long synthetic names and multiple rows.

Retain visible keyboard focus, semantic buttons, labels, disabled state and appropriate live regions. The early synchronous `locale-bootstrap.js` and `html.i18n-pending` no-flash rule must remain. Time display/filter semantics remain Asia/Shanghai.

## Ordered implementation and validation plan

1. **Audit:** Confirm the baseline and inventories above before styling. Preserve all behavior hooks and existing business information architecture.
2. **Foundation:** Evolve `app.css` into tokens/base/layout/components/utilities/page exceptions. Unify controls, state badges, tables, modal, alerts, toast styling, pagination, loading and empty states. Run Node regression tests and `git diff --check`.
3. **Shell:** Apply restrained topbar/sidebar/navigation hierarchy, compact page header/project context, bounded main content and responsive drawer behavior. Inspect Login, Workspace, Requirements, Test Cases, Collaboration, Admin and System in a real browser.
4. **Shared adoption:** Annotate actual machine statuses, identifiers, timestamps/numbers and existing selectable rows; adopt the shared visual system without rebuilding workflows or introducing new features. Repeat browser acceptance across execution/defects/automation/credits/logs.
5. **Regression:** Exercise ADMIN creation, five-step setup, ordinary-user permissions, local errors, 25-row task pagination and stale-response protection. Confirm context-safe resources and APIs using the same WAR at ROOT and `/veriqra`.
6. **Final gates:** Run Node tests, Maven tests, isolated MySQL tests and development packaging, responsive/locale/accessibility review and `git diff --check`. Record real counts and browser results; clean temporary databases, credentials, Tomcat directories and fixture assets. Retain non-sensitive evidence and leave the working tree for review without commit/push/deployment.

The six baseline frontend test files define 32 tests for R5.3-A pagination/stale responses/permissions/local errors/setup, project creation, authentication, locale/time/context semantics, System fields and access-log formatting. Their VM mocks do not establish actual DOM usability or visual quality. The new `design-system.test.js` adds baseline HTML contract checks, navigation/context/locale safety, catalog coverage, token contrast and archived status semantics; it deliberately avoids pixel snapshots and whole-CSS expectations.
